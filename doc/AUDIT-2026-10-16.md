## 1. Temuan Kritis (perbaiki segera)

### 1.1 Password database Supabase ter-commit ke repositori
File `scripts/find-pooler.ts` baris 24 berisi connection string lengkap dengan password database production (`postgres.pzpujzgjifynxsifsdyr:...@...pooler.supabase.com`). File ini ter-track di git dan password sudah ada di riwayat sejak commit `09fb3c4`. Remote repo mengarah ke GitHub (`Bisbiss/wabot`); repo tidak dapat dibuka tanpa akses, jadi kemungkinan private, tetapi setiap kolaborator dan setiap clone tetap memegang password ini.

Dampak: siapa pun yang punya akses ke repo (atau riwayatnya) mendapat akses penuh baca-tulis ke seluruh database, melewati semua autentikasi aplikasi.

Tindakan:
1. Rotasi password database di dashboard Supabase sekarang juga. Mengubah kode saja tidak cukup karena password sudah ada di riwayat git.
2. Hapus `scripts/find-pooler.ts` atau ubah agar membaca dari `process.env.DATABASE_URL`.
3. Pertimbangkan `git filter-repo` untuk membersihkan riwayat, lalu force-push, jika repo pernah dibagikan.

### 1.2 Webhook WAHA tanpa verifikasi, dan `userId` bisa dipilih penyerang
`src/app/api/waha/webhook/route.ts` menerima POST dari siapa saja tanpa memverifikasi HMAC/signature dari WAHA. Parameter `?userId=` dan `?session=` dari query string langsung dipakai untuk memilih tenant mana yang memproses pesan.

Dampak: penyerang yang tahu URL webhook (URL ini ditampilkan di halaman Gateway dan didaftarkan ke WAHA) bisa:
- Menyuntikkan pesan palsu atas nama nomor pelanggan mana pun ke tenant mana pun.
- Memicu bot membalas ke nomor sembarang (spam keluar dari nomor WhatsApp Anda, risiko banned).
- Menguras kuota API LLM Anda, karena setiap pesan palsu memanggil provider LLM berbayar.
- Mengubah data CRM (nama, stage, status PAID) lewat ekstraksi entitas dari teks palsu.

Tindakan: aktifkan HMAC di konfigurasi webhook WAHA (`hmac.key`) dan verifikasi header `X-Webhook-Hmac` di route sebelum memproses. Abaikan `userId` dari query; resolusi tenant cukup dari `session` yang sudah diverifikasi.

### 1.3 Secret cron default ter-hardcode dan dipublikasikan
`src/app/api/followup/trigger/route.ts` baris 84-85 selalu menerima `KATA_KUNCI_RAHASIA` dan `LC_CRON_SECRET` sebagai secret yang valid, meskipun `CRON_SECRET` di env sudah diset. Nilai itu bahkan ditampilkan di pesan error 401 dan di UI halaman Automation.

Dampak: siapa pun bisa memanggil `GET /api/followup/trigger?secret=KATA_KUNCI_RAHASIA&userId=<uuid>` dan memaksa bot mengirim pesan follow-up ke semua kontak tenant mana pun, berulang kali.

Tindakan: hapus kedua default, wajibkan `CRON_SECRET` dari env, kembalikan 500 jika belum diset. Hilangkan parameter `userId` saat autentikasi via secret, atau batasi hanya untuk pemanggil cron internal.

### 1.4 Endpoint AI bisa dipakai tanpa login
- `src/app/api/ai/test-chat/route.ts`: tidak ada pemeriksaan auth sama sekali. Siapa pun bisa memanggil LLM berbayar Anda tanpa batas, dan karena `userId` tidak dikirim, fungsi jatuh ke `aiConfiguration.findFirst()` yaitu config tenant pertama di database.
- `src/app/api/ai/test-connection/route.ts`: tidak ada auth. Menerima `providerBaseUrl` sembarang lalu melakukan fetch dari server dengan API key dari body atau dari database. Ini SSRF plus kebocoran API key tenant pertama ke URL yang ditentukan penyerang.
- `src/app/api/waha/qr/route.ts`: tidak ada auth. Siapa pun bisa mengambil QR code sesi mana pun dengan `?session=usr_xxx` dan mengambil alih nomor WhatsApp tenant tersebut dengan memindainya.
- `src/app/api/waha/send-test/route.ts`: `getAuthenticatedUser()` dipanggil tetapi hasilnya tidak diperiksa. Pengguna anonim tetap bisa mengirim pesan WhatsApp ke nomor mana pun lewat sesi default.

Tindakan: ganti semua ke `requireAuthUser()` dan pastikan sesi yang diakses milik user tersebut.

### 1.5 API key LLM disimpan dan dikembalikan dalam teks biasa
Kolom `api_key_encrypted` di tabel `ai_configurations` sebenarnya menyimpan plaintext. `GET /api/ai/config` mengembalikan `apiKey` utuh ke browser. Begitu juga `wa_sessions.api_key` dikembalikan utuh oleh `GET /api/waha/session`.

Tindakan: enkripsi at-rest (misalnya AES-GCM dengan key dari env), dan kembalikan hanya versi tersamar (`sk-...abcd`) ke klien.

## 2. Temuan Tinggi

### 2.1 Isolasi multi-tenant bocor di beberapa jalur
Sistem dirancang multi-tenant (`userId` di setiap tabel), tetapi ada banyak fallback yang melompat antar tenant:
- `src/lib/gateway/index.ts` baris 36-38: jika sesi tidak ditemukan, pakai `waSession.findFirst()` yaitu sesi tenant lain. Pesan bisa terkirim lewat nomor WhatsApp tenant lain.
- `src/lib/ai-agent.ts` baris 352-369: jika tenant belum punya config atau dokumen, pakai config/knowledge base tenant lain. Tenant A bisa menjawab pelanggan dengan API key dan materi milik tenant B.
- `src/lib/bot-pipeline.ts` baris 949-980: webhook tanpa `userId`/`session` akan mencari kontak di semua tenant berdasarkan nomor telepon, lalu fallback ke "sesi CONNECTED terbaru".
- `src/app/api/broadcast/groups/route.ts` baris 177-198: mengembalikan daftar semua `wa_sessions` (termasuk `apiUrl` dan `userId` tenant lain) ke klien, dan parameter `?session=` dari klien dipakai tanpa cek kepemilikan. User bisa broadcast lewat sesi tenant lain. Ada juga fallback ID hardcode `usr_8132a4c90ed7`.
- `src/app/api/waha/session/route.ts` baris 282: `apiUrl` per tenant disimpan, tetapi `src/lib/waha.ts` mengabaikannya; semua fungsi (`getWahaQr`, `getWahaMe`, `startWahaSession`, dll.) selalu memakai `WAHA_BASE_URL` global dan `WAHA_API_KEY` global. Fitur "custom gateway per user" tidak benar-benar berfungsi.

### 2.2 Prisma schema tidak sinkron dengan database yang berjalan
Tidak ada folder `prisma/migrations`. Skema dikelola lewat tiga sumber yang saling berbeda: `prisma/schema.prisma`, `prisma/supabase_schema.sql`, dan `scripts/migrate*.ts`. Contoh perbedaan: SQL `wa_sessions` tidak punya `user_id`, `gateway_type`, `api_url`, `api_key`; SQL `follow_up_rules`, `knowledge_documents`, `ai_configurations` tidak punya `user_id`; tipe `BIGSERIAL` di SQL versus `Int` di Prisma.

Tindakan: pilih satu sumber kebenaran. Jalankan `prisma migrate dev --name init` untuk membuat baseline, lalu hapus `supabase_schema.sql` dan `scripts/migrate*.ts`.

### 2.3 Default `userId` ter-hardcode di schema
Setiap model punya `@default("2dddb6d7-eb94-4056-9fe3-e13dca2f4e71")` untuk `userId`. Jika ada kode yang lupa mengisi `userId`, data diam-diam masuk ke akun developer, bukan error. `prisma/seed.ts` memang mengandalkan ini.

### 2.4 Kerentanan dependensi
`npm audit` melaporkan 1 critical dan 5 high, antara lain:
- `next@16.3.3`: SSRF di Image Optimization, cache poisoning SSG/ISR, information disclosure. Fix: `next@16.4.2`.
- `sharp`: CVE di librsvg. Fix tersedia via `npm audit fix`.
- `source-map-js`: DoS event loop. Fix via `npm audit fix`.
- `mammoth` membawa `sprintf-js` rentan DoS (moderate).

Tindakan: `npm audit fix`, lalu upgrade `next` dan `eslint-config-next` ke 16.4.x secara manual dan uji.

### 2.5 Tidak ada rate limiting atau batas ukuran
- Upload knowledge (`/api/ai/knowledge/upload`) tidak membatasi ukuran file; PDF besar akan di-parse penuh di memori.
- Webhook, test-chat, dan login tidak dibatasi laju.
- `POST /api/broadcast/groups` dan `/api/followup/trigger` berjalan sinkron dengan `setTimeout` per grup; broadcast 100 grup dengan delay 3 detik berarti request HTTP 5 menit. Di Vercel/Netlify ini akan timeout di tengah jalan dan campaign tertinggal berstatus `SENDING` selamanya.

## 3. Temuan Menengah

### 3.1 Kredensial demo di halaman login
`src/app/login/page.tsx` baris 22-23 mengisi otomatis `admin@wabot.id` / `1234567890`. Jika akun itu benar ada di Supabase, ini adalah kredensial yang terpublikasi. Mode "Supabase belum dikonfigurasi" juga langsung mengarahkan ke dashboard tanpa auth; middleware pun melewatkan semua request ketika env kosong (`isConfigured === false`). Deploy dengan env salah berarti dashboard terbuka untuk publik.

### 3.2 URL Supabase production ter-hardcode sebagai fallback
`src/lib/supabase/client.ts` dan `server.ts` memakai `https://pzpujzgjifynxsifsdyr.supabase.co` jika env kosong. Middleware juga menerima `SUPABASE_SERVICE_ROLE_KEY` sebagai pengganti anon key, yang berarti service role key bisa dipakai untuk sesi cookie klien jika anon key lupa diset.

### 3.3 Open redirect di auth callback
`src/app/auth/callback/route.ts` memakai `?next=` langsung tanpa validasi bahwa nilainya path relatif. `next=//evil.com` menghasilkan redirect keluar domain.

### 3.4 Header `Host` dipercaya untuk membangun URL webhook
`getWebhookBaseUrl` di `src/lib/waha.ts` memakai `x-forwarded-host`/`host` dari request jika `WEBHOOK_BASE_URL` kosong. Penyerang bisa mendaftarkan webhook WAHA ke host miliknya lewat satu request `action: "create"`. Wajibkan `WEBHOOK_BASE_URL` di production.

### 3.5 Pesan error internal bocor ke klien
Hampir semua route mengembalikan `error.message` mentah (termasuk pesan Prisma yang memuat nama tabel/kolom) dengan status 500.

### 3.6 Validasi input minim
Tidak ada schema validation (zod atau sejenis). Contoh: `PATCH /api/contacts/[id]` menerima `leadStatus`, `handlingStatus`, `sentiment` bebas; `POST /api/ai/config` menerima `providerBaseUrl` sembarang (server lalu fetch ke sana, SSRF dari user terautentikasi); `parseInt(body.maxTokens)` tanpa batas.

### 3.7 Logika pipeline
- `wahaMessageId` fallback memakai `Date.now()+random` sehingga idempotency tidak berlaku untuk payload tanpa ID. Simulator mengirim `id: sim_...` yang unik per klik, aman, tetapi WAHA retry tanpa ID akan diproses ganda.
- Deteksi "SUDAH TRANSFER" di `enrichExtractedEntities` menimpa output LLM dan langsung menandai `PAID` / skor 100 hanya dari kata kunci teks pelanggan, tanpa verifikasi admin. Dashboard funnel "Terdaftar" bisa diinflasi oleh siapa pun yang mengetik kalimat itu.
- `extracted_target` diisi seluruh teks pesan jika mengandung kata kunci (misalnya "ui" atau "its"), sehingga kolom `target_campus_major` terisi kalimat panjang yang tidak relevan. Kata "ui" dan "its" juga cocok dengan substring kata biasa.
- Follow-up trigger membuat `message` tanpa `wahaMessageId` (null), lalu `prisma.message.create` memakai unique nullable; aman di Postgres tetapi perlu disadari.
- `/api/messages` menebak LID dari `wahaMessageId contains "@lid"`, heuristik rapuh.

### 3.8 Dashboard menampilkan data palsu saat API gagal
`src/app/page.tsx` baris 65-80 menampilkan metrik dummy (3 kontak, 85% otomasi, 2.8 detik) jika fetch gagal atau 401, tanpa indikator bahwa itu bukan data asli. `avgResponseTimeSec` di API pun hardcode `2.8`.

## 4. Kualitas Kode dan Pemeliharaan

- **Tidak ada test sama sekali.** Fungsi murni seperti `formatChatId`, `isWhatsAppLid`, `validateAndCleanCustomerName`, `extractCustomerNameFromText`, `normalizePhoneNumber`, dan `isDirectPersonalChat` sangat cocok untuk unit test dan merupakan inti logika bisnis.
- **158 error lint** tidak akan lolos `next build` jika lint diaktifkan di CI. 144 adalah `any`, 43 variabel tak terpakai, 10 `set-state-in-effect`.
- **Halaman monolit**: `contacts/page.tsx` 1129 baris, `broadcast/page.tsx` 1064 baris, `ai-settings/page.tsx` 903 baris, semuanya `"use client"` dengan state lokal. Sulit diuji dan dipelihara.
- **Kode mati**: `src/components/Navbar.tsx` tidak dipakai (digantikan `Sidebar` + `TopHeader`). Kolom `authUsername`/`authPassword` di `WaSession` tidak pernah dipakai. Interface `IGatewayAdapter.getStatus/getQr/logout` tidak dipanggil dari route.
- **Duplikasi**: logika `getWahaQr` dan `qr/route.ts` hampir identik (dua kali, untuk endpoint utama dan fallback). Pola "coba endpoint A, fallback B" diulang di 6 fungsi. Pembuatan `WaSession` default diulang di 3 tempat.
- **Raw SQL untuk broadcast** (`$queryRawUnsafe` dengan parameter, aman dari injeksi) padahal model Prisma `BroadcastCampaign` sudah ada. `update_gateway_config` juga pakai `$executeRaw` padahal bisa `prisma.waSession.update`.
- **Polling agresif**: inbox polling pesan tiap 3 detik dan daftar kontak tiap 6 detik; gateway tiap 10 detik, dan setiap panggilan `/api/waha/session` melakukan 3-4 HTTP call ke WAHA. Dengan beberapa tab terbuka, WAHA akan dibanjiri.
- **N+1 di analytics**: 12 query `count` berurutan; bisa jadi 1-2 query `groupBy`.
- **Import kontak** melakukan `findUnique` + `create` per baris, hingga 2000 baris, tanpa transaksi.
- `README.md` masih template bawaan `create-next-app`. Tidak ada dokumentasi setup WAHA, env, atau deploy.
- `tsconfig.tsbuildinfo` dan `next-env.d.ts` ada di `.gitignore` tetapi perlu dicek tidak ter-track (saat ini aman).

## 5. Hal yang Sudah Baik

- Hampir semua route CRUD menggunakan `requireAuthUser()` dan memfilter `userId` dengan benar (contacts, knowledge, rules, messages, analytics, history).
- Raw SQL memakai parameter terikat, tidak ada string concatenation dengan input user.
- Pipeline menyimpan pesan ke database sebelum mengirim ke WAHA, sehingga kegagalan gateway tidak menghilangkan data.
- Pemisahan adapter gateway (`IGatewayAdapter`) memberi jalan untuk provider lain.
- Delay anti-ban pada broadcast dan follow-up.
- `.env` tidak pernah ter-commit; `.gitignore` sudah benar.
- TypeScript strict mode aktif dan lulus typecheck.
